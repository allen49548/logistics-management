# 小票识别与去重规则

> **2026-11-14 起**：所有司机共用一个「物流部」混合群，「群 = 某司机」作废。
> 每笔费用必须先解析**司机归属**（按消息发送者），再进入金额抽取与去重；
> `driver` 参与业务键，因此归属错误会直接破坏去重正确性。
>
> **弹性司机（2026-11-14 定案）**：司机增减是弹性的，名册只是归属辅助、不是前置门槛。
> **只统计本轮/本月实际发了付款凭证截图的司机**，不铺全员名册、不列 0 笔司机、
> 不纠结全员到齐或 open_id 补齐。名册外的真实群成员发图时，
> `driver_roster.py resolve` 按发送者姓名直接建立司机（`is_new_driver=true`），
> 无当年报表按 `record_without_write` 只登记台账、绝不新建报表；
> 群主本人 / 代发冲突 / 姓名形态异常仍进「待人工确认·未识别司机」。
>
> **状态口径**（`config.status_model`，详见 `references/notification.md` 第一节）：
> 只有「已登记·待打款」（台账已登记且 `reimbursed=0 AND voided=0`）计入未报销 / 未结金额；
> 手写票、纯文本、需补材料、重复提交、作废**一律不进任何合计**。
> `scripts/ledger.py balance` 按司机输出滚动「我的未结」，**只供负责人专业版与台账查询使用**；
> 面向司机的通报按 `config.driver_message` 极简口径，只写本次报销金额和日期，不展示四态与未结。

## 一、纳入识别的消息（只认付款凭证截图）

`config.ocr.accepted_source = payment_voucher_screenshot`。**先判来源类型，再决定是否抽金额**。

| 消息 / 图片类型 | 处理 |
|---|---|
| `image` / `post` 内嵌图 / `file` 图片，且为**机打付款凭证截图**（微信/支付宝账单详情、支付成功页、机打收据等） | 下载后逐张识别 → 正常流程 |
| **ETC 充值成功截图**（标题「充值成功」、含成功充值金额/时间/ETC卡号/当前卡片余额，微信钱包等机打版式） | **按正常付款凭证处理**：正常抽金额入账、登记台账、写「报销明细」sheet，类别记为 `ETC充值`。不进「待人工确认」、不因「充值非通行消费」拦截。2026-11-16 22:39 用户定案为规则变更。 |
| **手写票**（手写收据、手写账目草稿、手写计算纸、票面手写金额） | **一律不记录**：不入账、不登记台账、不把金额列入「待人工确认」。记入「补录提醒」清单，并在唯一的「物流部」群通报里**按司机分节**提醒「请改发付款凭证截图补录」 |
| **纯文本 `text` 报销消息**（即使含「报销 + 金额」） | **一律不记录**：不作为报销记录、不登记台账，只记入清单「跳过·文本报销不记录」，**不算异常** |
| 非票据图片（群公告横幅、表情、风景等） | 跳过，记入清单「跳过项」，**不算异常** |
| `system` / 已撤回 | 跳过，**不算异常** |
| 付款凭证截图，但**发送者无法归属到司机名册 / 归属冲突** | 进「待人工确认·未识别司机」：不自动写入、不登记台账、不猜归属、不默认算给某个人 |

判定要点：票面金额/日期是否为**印刷体**、是否有支付平台版式（交易单号、支付时间、商户名）。只要关键金额是手写的，就按手写票处理，不尝试读金额。

已撤回消息正文不可恢复，**不猜数**。一条消息含多张图 → 每张独立成一条候选记录。

## 一之二、司机归属判定（混合群，先于金额抽取）

「群名决定司机」已作废。每条候选记录在处理金额前，先用 `scripts/driver_roster.py resolve` 解析 `driver`：

```
python3 scripts/driver_roster.py resolve \
  --sender-id <消息 sender.id> \
  --sender-name <发送者姓名> \
  --text <同条消息的文字 / 票据描述> \
  --receipt-name <票面付款人姓名，可无>
```

- 名册 = 报表目录下 `{司机}{年份}.xlsx` 文件名前缀 + `driver_roster.extra_drivers` + 已登记 `members` + 台账出现过的司机；**精确匹配，不做模糊匹配**。
- 每轮先跑 `driver_roster.py sync` 从物流部群成员同步 `open_id → 司机`；新司机进群且姓名与名册一致即自动纳入。
- 群主本人（`owner_open_id`）不算司机；他发的凭证不自动归属，进待人工确认。
- 文字 / 票面出现**其他**司机姓名 → 判 `conflict`（疑似替他人代发），进待人工确认；open_id 与姓名解析出不同司机也判 `conflict`。
- 发送者不在名册 → 判 `unknown`，进「待人工确认·未识别司机」；文字里提到的姓名**只作线索**，不自动归属。
- 返回的 `has_report` / `report_action` 决定后续走 `write` 还是 `record_without_write`（**绝不新建报表**）。
- 以上 `unknown` / `conflict` 情形都**不写入、不登记台账、不列入金额待确认**，只在清单与负责人专业版列明原因；司机版只在一行「小提示」里简单提醒「请注明本人姓名」。

## 二、视觉识别提示词（逐张调用 ViewImage）

要求模型返回结构化信息，不凭常识补内容：

```
逐字转录这张付款凭证截图的所有可见文字。输出：
1) 来源类型：是否机打付款凭证截图 / 是否手写票（关键金额为手写则判手写票）/ 非票据图；
2) 全部金额数字及其含义（合计/总计/实付/单项/找零/单价）；
3) 开票或消费日期（原样转录，并给出 YYYY-MM-DD 归一化结果；无日期写 none）；
4) 付款人/司机姓名（没有写 none）；
5) 费用类别（油费/高速/停车/维修/餐费/其他/未分类）；
6) **订单号 / 交易单号 / 微信支付交易号 / 商户单号**（完整数字串，原样转录；没有写 none）——用于去重，必须尽量抽全；
7) 每个关键字段的置信度 0–1，特别是金额、日期与订单号；
8) 是否有涂改、遮挡、重叠、多张票叠拍。
不要推测、不要补全模糊数字；看不清就写「无法辨认」并给出低置信度。
```

## 三、字段与金额抽取

每条候选记录字段：

```
message_id, chat_id, driver, image_path, image_sha256, phash,
receipt_date, amount, category, order_no, pay_time, summary, handwritten, confidence, source
```

- **`order_no`（订单号 / 交易单号）是去重主依据，付款凭证截图必须尽力抽取**：机打凭证（微信/支付宝账单、支付成功页、机打小票）几乎都带订单号，抽全后业务键 = `driver|pay_time|order_no`，司机隔天重发同一凭证也能精准判重，绝不重复计算。抽不到订单号时回退 `driver|receipt_date|amount|category|image_sha16`，并标注置信度下降。
- `pay_time` 取支付时间（精确到秒最佳）；无则回退 `receipt_date`。
- `driver` **由消息发送者经 `driver_roster.py resolve` 解析**（见「一之二」），不再由群决定。票面 / 文字明确写他人姓名且与发送者不一致 → 判 `conflict`，进待人工确认，**不自动改写归属**。未识别司机一律不进入金额抽取与写入流程。
- `amount` 取**合计 / 总计 / 实付 / 金额**；无合计时取最大单项，但 `confidence` 降一级并标注「按最大单项取数」。排除找零、余额、单价×数量的乘积误读、手机号、车牌、日期数字。
- 数字清洗：去 `¥ 元 ,` 与空格；手写易混 `0/6`、`1/7`、`7/9`、`3/8` 必须靠上下文交叉验证；出现两个及以上候选金额且无法区分 → 低置信度，不自动写入。
- `receipt_date`：票面日期优先，兼容 `2026.11.3`、`11/3`、`11月3日`、`2026-11-03`；`3/11` 这类无法判定月日顺序 → 无法辨认。**无日期一律进「待人工确认」，不按消息时间自动归类**（config 的 `undated_receipt=manual_review`）。
- `category` 无法判断填「未分类」。

**置信度门槛**：付款凭证截图 `min_confidence=0.8`（config 现只保留此门槛；手写票不再识别金额，故不再设手写置信度门槛）。低于门槛、有涂改/遮挡/叠拍、金额或日期无法辨认，一律进「待人工确认」清单，**绝不自动写入**，并在通报里列出金额与图片文件名供人工核对。

**手写票处理（重要）**：手写票不进入金额抽取与置信度判定，直接判为「补录提醒」。通报里说明「该张为手写票，未计入；请改用付款凭证截图（含金额与支付时间）重发到本群补录」，附图片文件名与消息时间。不得根据手写数字自行认定金额后写入。

## 四、三方池六层去重（按顺序执行）

> **2026-11-17 21:50 用户定案**：「查重复要结合新增的数据和群里的历史数据有没有重复！」
> 去重池从「只有台账」扩为**三方**：台账 `entries` + 群历史池 `voucher_seen` + 各司机报表「报销明细」既有行。
> **命中任一池一律跳过**（`dedup.history_hit_policy=skip_always`），含历史当时并未入账的笔。

**A. 台账池（已入账）**

1. **L1 message_id**：`ledger.py check --message-id`。命中 → 已处理过，跳过。
2. **L2 image_sha256**：下载文件字节的 SHA-256。同一张图被转发到多个群/重复发 → 命中，记「重复报销·同图」。
3. **L3 感知哈希**：`phash`（缩放到 32×32 灰度后 DCT 或 dHash），与台账中近 90 天记录的汉明距离 ≤ `phash_hamming_threshold`（默认 6）即视为同一张票（应对不同压缩、裁切、截图边缘）。PIL 不可用时跳过本层，并在清单注明。
4. **L4 业务键 / 订单号**：机打凭证优先用 `driver | pay_time | order_no`（订单号唯一）；无订单号才回退 `driver | receipt_date | amount | category | image_sha16`。相同金额不是重复，只有订单号+支付时间一致才算同一笔。同一笔报销换一张图、或同群连发两次 → 命中，记「重复报销·同业务键」。

**B. 群历史池（群里出现过，不一定入过账）**

5. **L5 群历史池 `voucher_seen`**：按 订单号 → 同图 SHA → 感知哈希（阈值同 L3）→ `driver+receipt_date+amount(+category)` 四同，在历史池里找同笔。命中返回 `original_source="群历史"` 与 `original_status`：`已入账` / `群里出现过·未入账`。
   - 覆盖场景：台账建立前（本机台账最早 2026-11-13）发出的凭证、台账登记出错漏记的笔、当时被判手写票/待确认/未识别的笔、旧群里发过后迁移到物流部群重发的笔。
   - **即便历史那次没入账，也判重复跳过**（用户 2026-11-17 定案），只在清单注明「群里出现过·未入账」，不二次入账、不补录。

**C. 报表明细池（台账漏记兜底）**

6. **L6 报表明细既有行**：读该司机当年报表「{月}报销明细」sheet 的既有行（含隐藏唯一键、订单号、日期、金额、类型），按 `唯一键=message_id` / 同订单号 / 同日同额同类型 比对。命中返回 `original_source="报表明细"`、`original_status="已入账"`。
   - 用途：台账被重建、迁移、误删，或早期手工写表时，报表仍是最硬的账；本层保证「报表里有过的笔绝不会被再加一次」。
   - 报表缺失（`report_root` 无该司机文件）时本层自动跳过，不中断去重。

**D. 历史池维护（每轮必做）**

- 本轮在群里拉到的**每一张票**判定完后都要落池：`ledger.py index-add --json '[...]'`（幂等键 `message_id`）。`status` 取值 `entered` / `pending` / `skipped` / `unknown_driver` / `non_voucher`；手写票、纯文本报销、非票据图同样入池并记原因，下次同图重发才能拦住。
- 入账时 `ledger.py add` 会自动同步该笔进池（`status=entered, report_written=1`），无需额外调用；作废（`void`）后池内状态由后续 `index-backfill` 标记 `voided`，`voided` 状态不会被普通 upsert 覆盖。
- 首次启用、换机、或怀疑池缺失：`ledger.py index-backfill`（台账 + 报表明细全量回填）+ `ledger.py index-stats` 核对规模。

补充规则：

- **批内去重（新增数据之间）**：同一次运行的多条候选若同订单号 / 同图 SHA / 感知哈希近似 / 司机+日期+金额+类别相同，**`check-batch` 自动只保留首次出现那条**，其余返回 `layer="B-…"`、`original_source="本批"`、`original_status="本轮已出现·不重复计算"`，记「批内重复」。无需人工比对，人工比对容易漏。
- **跨天重发（核心防重复场景）**：司机某天发的凭证，负责人还没点完成报销，隔几天又把同一张发到群里 → 命中 L2（同图）/ L3（同版式）/ L4（同订单号）/ L5（群历史池）/ L6（报表明细）任一层，判为重复提交并跳过。**这是报销归集最忌讳的情形，必须坚决不重复计算**。命中时 `ledger.py check` 会返回 `original_created_at`（原出现/登记时间）、`original_status`（已入账 / 群里出现过·未入账）、`original_source`（台账/群历史/报表明细）、`original_amount`；清单须在「⚠️ 重复提交·未重复计算」段落逐项写明这四项。
- 文本报销无图 → 只用 L1 + L4 + L5（按司机+日期+金额）。
- 同一司机跨群 / 跨批次同业务键也算重复（历史停用群里已登记的凭证，司机迁移到物流部群后重发仍判重复）；**不同司机即便金额、日期、类别完全相同也不判重复**——业务键与各池比对都含 `driver`，「相同金额不是重复」在混合群下同样成立。
- 命中任一层即记 `duplicate_of` 与原因，**不再写报表、不再登记台账**；通报只在清单留痕（2026-11-16 20:21 起重复项不进群内与负责人私聊通报）。
- 低置信度记录**不登记台账**，下次运行仍会出现在待确认清单，直到人工确认或删除消息——这是预期行为，避免永久埋没一笔真实报销。

## 五、台账写入时机

只有 **写入报表成功且回读校验通过** 才执行 `ledger.py add`。写入失败、跳过、待确认（含未识别司机）一律不登记，保证下次可重试。台账字段含：message_id、chat_id、driver（**解析出的司机名**）、receipt_date、amount、category、image_sha256、phash、business_key、报表文件、sheet、单元格、旧值、新值、写入时间、运行 ID。

**月度统计口径**：`monthly_summary.py` 直接按台账 `entries.driver` 分组，**与群白名单完全解耦**；停用旧群的历史条目仍按司机计入；**只列当月实际有凭证的司机**，不再 union 全员名册、不列 0 笔司机、不写零值提示。对比月数据仍单独计算，仅供负责人专业版环比。

这是**一次性的业务特批**，不是规则变更：本文「只认付款凭证截图、手写票不记录、
纯文本不记录、低置信度/无日期进待人工确认」等判定规则**逐字不变**。

并在台账该批条目 `note` 留痕；**绝不把例外写成通用规则、不在司机群加说教文案**。

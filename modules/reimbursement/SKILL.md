## 艾特（@）触发：群/内容门槛 + 权限分级 + 先调侃回应（2026-11-16 用户定案，铁律）

**用户原话**：①「负责人艾特机器人，权限是可以处理异常和修改规则，司机艾特只能处理正常报销，不能更改规则和修改代码！」②「任何人艾特你要先回应一句调侃的收到，再执行任务，回应有温。」③「飞书艾特你要根据特定的群和内容再执行任务。」

**铁律一：先回应，再执行（ack-first）**
- 任何人 @ 机器人（负责人或司机），**第一步必须先发一句调侃、有温度的「收到」到主群**（`mention.py ack --send`），然后才进入报销归集或规则处理流程。绝不闷头干活不吭声。

- ack 幂等键 `<prefix>-ack-<run_id>-<chat_id前8位>`，重跑不重复刷屏。

**铁律二：权限分级（最小权限）**
- 判定以**发送者 open_id** 为唯一客观身份（`mention.py classify`），绝不靠姓名猜管理员：

### 状态口径（区分「报销完成 / 未报销」，2026-11-14 定案）

## 执行流程

1. 读 `config.json`；用系统 `date` 取当前时间，计算拉取窗口 `[now - lookback_days, now]`（ISO 8601 带 `+08:00`）。不凭记忆推算日期。
2. 动态发现群（`+chat-list --as user`）→ 与白名单合并；核对主群仍是 `chat_discovery.primary_chat_id`，停用群一律不纳入读取。发现其他符合条件的新群时沿用「首次发现」规则：只写 `notify=false` 并向降级私聊报告，不发群消息。
3. **可选同步名册**（`driver_roster.py sync`，仅提升归属精度，不是入账前置条件、也不催全员到齐），再只对**物流部**一个群拉消息（`--download-resources` 会把图片存到 cwd 下 `lark-im-resources/`；`post` 内嵌图片同样会下载）。忽略 system 消息与已撤回消息（正文不可恢复，记「跳过·已撤回」，不猜数）。**纯文本（`text`）报销消息一律跳过**：即使含金额也不作为报销记录、不登记台账，只在清单记「跳过·文本报销不记录」，不算异常。
4. 逐张图片用视觉识别（ViewImage）先判定**来源类型**，规则见 `references/ocr-and-dedup.md`；同时**逐条先解析司机归属**（第 4 步之前完成 `resolve`）：
   - **付款凭证截图**（机打）→ 抽取金额/日期/订单号/文字描述，进入正常流程。
   - **手写票 / 手写收据 / 手写草稿** → **一律不记录**（不入账、不登记台账、不进待人工确认金额），记入「补录提醒」清单，并按**司机分节**提醒「请改发付款凭证截图补录」，附图片文件名与消息时间便于定位。
   - 非票据图片（群公告、横幅、表情等）跳过且不算异常。
   - 低置信度、无日期、涂改遮挡的付款凭证进「待人工确认」，不自动写入。
   - **未识别司机 / 归属冲突** → 进「待人工确认·未识别司机」，不自动写入、不登记台账，并在专业版列明原因。
5. **三方池查重**（2026-11-17 21:50 用户定案：新增数据必须与群历史数据比）：`scripts/ledger.py check` 覆盖 6 层——台账 `entries`（L1 message_id → L2 图片 SHA-256 → L3 感知哈希 → L4 订单号/业务键）→ **L5 群历史池 `voucher_seen`**（订单号 / 同图 / 感知哈希 / 司机+日期+金额+类别，覆盖当时跳过或未入账的历史凭证）→ **L6 报表明细既有行**（台账漏记兜底）。**每条必须带 `--driver`、`--receipt-date`、`--category`**，否则 L5/L6 退化为只比订单号与图片。
   **批量去重（性能，2026-11-17）**：本轮凭证 ≥ 2 条时优先用 `scripts/ledger.py check-batch --json '[...]'`（或 stdin 传 JSON 数组），一次进程去重全部凭证，省掉 N 次进程启动 + N 次 config 解析 + N 次 SQL 连接；结果数组与逐条 `check` 完全同构（`{"duplicate":bool,"layer","entry",...}`），字段语义逐字一致，无需改下游解析。单条仍可用 `check`。
   **批内也会判重（新增数据之间）**：`check-batch` 自动比对本轮已通过的凭证，同订单号 / 同图 / 感知哈希近似 / 司机+日期+金额+类别相同即返回 `layer="B-…"`、`original_source="本批"`，只保留首次出现那条，无需人工比对。
   **去重以订单号 + 支付时间为准，相同金额不是重复**：只有当订单号相同（机打小票）或「无订单号时 司机+日期+金额+类别+图片哈希」完全相同，才判为重复并记「重复报销·已跳过」，不再写入。L3/L5 感知哈希命中但订单号不同，视为同版式截图误报，不算重复；**不同司机即便金额与日期相同也不判重复**（业务键与各池比对都含 driver）。
   **命中一律跳过（用户 2026-11-17 21:50 定案）**：群历史里出现过、报表里已有，即便该笔当时**并未入账**（跳过/待确认），本轮也判重复、不补录。`check` 返回 `original_source`（群历史 / 报表明细）、`original_status`（已入账 / 群里出现过·未入账）、`original_created_at`。
   **重复命中必须透明（只进清单，不进通报）**：一旦命中重复，**只在运行清单**的「⚠️ 重复提交·未重复计算」段落**按司机分节**逐项列出：金额、命中池（台账/群历史/报表明细）、原出现时间、当前状态（已入账/未入账）、对应任务链接——**审计层面绝不允许静默跳过**。~~在群内与负责人私聊通报~~ **已作废**（2026-11-16 20:21）。
   **重发场景**：司机某天发的凭证、负责人还没点完成报销，隔几天又发同一张 → 命中 L2/L3/L4/L5/L6 任一层，判重复跳过；**只在运行清单**注明（不再进通报，2026-11-16 20:21）。
   **历史池维护（每轮必做）**：本轮拉取到的所有凭证判定完后，用 `scripts/ledger.py index-add --json '[...]'` 把每张票写入历史池（`message_id` 幂等），`status` 标 `entered`/`pending`/`skipped`/`unknown_driver`/`non_voucher`；手写票、纯文本报销、非票据图也要入池（记 skipped，附原因），保证下次同图重发能被拦住。换机/首次启用先跑 `index-backfill`（台账+报表明细全量回填）+ `index-stats` 核对。
6. 按小票日期确定年月（跨月按小票月份，不按运行月份），定位 `{报表根}/{年份}年/司机工资/{司机}{年份}.xlsx`。**不再定位原表里位置不一的「报销 / 报销支出」汇总单元格**（2026-11-14 23:53 用户新口径：统一建「报销明细」解决兼容问题）。`locate_report.py` 仍可只读用于审计，但其「报销项歧义 / 公式单元格 / 无有效数值」结果**不再阻断入账**。

## 月初月报（每月 1–4 号自动运行）

独立自动化「自动报销系统·月初月报」在每月 1–4 号 09:00 运行（RRULE：`FREQ=MONTHLY;BYMONTHDAY=1,2,3,4;BYHOUR=9;BYMINUTE=0`）。脚本 `scripts/monthly_summary.py` 自带「每自然月只真发一次」防护（`state/monthly_sent.json`）。

**口径（按司机分类 + 四态 + 弹性司机）**
- **统计直接按台账 `entries.driver` 分组，与群白名单完全解耦**：旧版靠遍历白名单群取 `driver`，单群模式下会漏掉所有司机。
- **只列当月实际发了付款凭证截图的司机**：不再 union 全员名册、不列 0 笔司机、不写「没列到名字的…」；司机增减是弹性的，不要求到齐。对比月数据仍单独计算，仅供专业版环比。
- 月份归属：以 `pay_time`（无则 `receipt_date`，再无则 `created_at`）所属月为准；统计「上个月」（`--month` 默认 = 当前月减 1）。
- 统计范围：该月所有 **未作废**（`voided=0`）报销条目；按 `config.status_model` 拆分 **已报销 / 已登记·待打款（唯一计入未结）**。**停用旧群的历史条目仍计入**（按司机归类，不按群）。
- **环比**：与再上一个月按司机逐一对比，给出金额差额与百分比（上月基数为 0 时写「新增」）；**只出现在负责人专业版**，群内版不写环比。
- 专业版每位司机单列「已打款 X 笔 ¥A / 待打款 Y 笔 ¥B」，全队给**未结合计**；金额不保密。
- 无当年报表文件的司机在专业版标注 `record_without_write 待指定`（含弹性新建的司机）。
- 每位司机额外采集该月**凭证日期列表**（`pay_time` → `receipt_date` → `created_at`，去重升序），供群内版显示日期。

**两层发送（与日常归集一致，群内版走极简渲染）**
`monthly_summary.py --send` 内部生成两类内容，用 `notify.py` **一次调用**发出：
- **群内总览**：一份到唯一 `notify=true` 的物流部群，只列当月有凭证的司机，按司机一行只写「姓名 ¥金额（日期）」＋合计＋一句安全驾驶调侃。
- **负责人专业版**：按司机分节明细 + 四态 + 合计 + 环比 + 台账/清单路径，**一字不减**。
- **不生成个人月报、不生成 manifest、不传 `--driver-dm-manifest`、不统计谁没到齐**；清单只保存两层渲染原文与发送结果。
- 群内版统一调用 `scripts/driver_copy.py`（`build_driver_data` 组装只有金额和日期的数据），保证与日常归集口径完全一致。

调用：`python3 scripts/monthly_summary.py --send --run-id <运行ID>`（或 `--compute` 仅看数据，`--month YYYY-MM` 指定月份，`--dry-run` 不真发）。结果写 `state/runs/monthly_<YYYY-MM>_<HHMM>.md`。

**流程优化与预期效果**（同一份固定输入、相同环境下重复测量的均值）：

| 优化点 | 做法 | 效果 |
|---|---|---|
| 月报两次全表扫描 → 一次 | `compute()` 改为一次连接、一次 `SELECT`，在内存中按目标月/对比月分组后再各自聚合；保留 `compute_month()` 兼容入口 | 月报计算 **约 0.57 ms → 0.27 ms（约 -54%）** |
| 台账重复 DDL → 结构指纹短路 | `connect()` 用 `PRAGMA user_version` + 列集合校验，结构已就绪时跳过建表/迁移/建索引；新库或缺列时仍完整迁移 | 单次连接 **约 1.58 ms → 1.47 ms（约 -7%）**；台账条目越多、调用越频繁收益越明显 |
| 司机名册重复扫目录 → 进程内缓存 | `report_drivers()` 按报表目录缓存，`save_config()` 自动失效 | **约 0.037 ms → 0.001 ms（-97%）**，一次归集内多次 `resolve` 不再反复 glob 磁盘 |
| 写报表统一布局解析 | 列位置/宽度/日期字段优先级一次解析后复用，不再多处硬编码列号 | 改列结构只改配置，无需改代码；减少重复推导 |
| 通知前机器人自检的群列表拉取 → TTL 缓存（2026-11-17） | `bot_check._bot_chat_list`：`lark-cli +chat-list --page-all` 结果按 TTL（默认 1800s，`LARK_BOT_CHECK_TTL` 可覆盖）缓存到 `modules/reimbursement/state/.lark_bot_check_cache.json`；`auth status` 仍每次实时查（约 0.12s） | 每次通知自检 **约 1.10s → 0.19s（省约 0.9s）**；机器人在群是稳定状态，无需每轮都拉全量群列表 |
| 逐条去重 → 批量去重（2026-11-17） | `ledger.py check-batch`：一次进程处理 N 条凭证（`--json` 或 stdin），四层去重语义与逐条 `check` 完全一致；同时 L3 感知哈希 `SELECT *` 收窄为只拉 7 个必要列 | 20 条凭证去重 **约 1.31s → 0.06s（省约 1.25s）**；省掉 N 次进程启动 + N 次 config 解析 + N 次 SQL 连接 |
| 台账单池 → 三方池六层去重（2026-11-17 用户定案「要结合新增数据和群里的历史数据」） | `ledger.py` 新增 `voucher_seen` 群历史池 + `index-add` / `index-backfill` / `index-stats`；`check`/`check-batch` 增 L5（群历史池）、L6（报表明细既有行）两层，新增 `--driver/--receipt-date/--category`；`add` 自动同步入池；config.dedup 增 `sources` 与 `history_hit_policy=skip_always` | 台账漏记/历史未入账/台账建立前的凭证重发不再重复入账；20 条批量去重仍 **0.06s**（现池 105 条） |
| 写报表 precreate_all 全量回读 → 无变化跳过（2026-11-17） | `reimb_detail.has_detail_sheet` 只解压 workbook.xml 判断是否已有新名明细 sheet；precreate_all 时「本轮无该司机新凭证且已有新名 sheet」的报表直接跳过 | 无新数据时不再对 8 个司机报表做完整 zip 重写 + openpyxl 回读（**约省 100ms+**，报表越多收益越明显）；缺 sheet 仍预建、旧名 sheet 仍迁移、有凭证仍写入，语义不变 |

**回归保证**：改造前后用 29 个固定场景（文案渲染、报表写入与幂等、台账统计与查重、名册解析、月报计算、任务、通知 dry-run）采集输出快照；忽略动态时间戳与临时目录后，**语义差异为 0**。真实报表未被测试写入（基线脚本只操作临时副本）。

## 边界

- **只读取唯一的「物流部」群**；只向 `chat_whitelist` 中 `notify=true` 的那个精确 chat_id 发司机版，绝不向停用旧群、门店群或非白名单会话发消息。
- **司机归属绝不猜**：名册内按 open_id/姓名精确匹配；名册外的**真实群成员姓名**按弹性口径直接建立司机（客观身份，不是猜）。文字/票面姓名与发送者冲突、群主本人发的、姓名形态异常或解析不出，一律进「待人工确认·未识别司机」，不写入、不登记台账。
- **司机弹性，不纠结全员到齐**：只统计发了付款凭证截图的司机；不催进群、不催 open_id、不把「谁没到齐」写成异常/待办/告警。无报表的新司机按 `record_without_write`，绝不新建报表。
- **报销费用最忌讳重复计算（铁律）**：以订单号 + 支付时间为唯一性依据，相同金额不是重复；任何命中四层去重的记录都必须跳过，且**只在运行清单**透明注明「原登记时间 + 是否已报销」（不再进通报，2026-11-16 20:21）。司机重发的同一凭证（即便隔天、负责人尚未完成）一律判重复，坚决不加钱。重复命中的原始 `message_id` 仍保留在台账（含已作废），不物理删除。
- **每轮统计后都发通报**（以顶部 2026-11-16 20:08/20:21 口径为准）：有**新入账**→群内简洁总览（无 @/任务/权限，不含重复旧凭证）；无新入账（含纯重复提交）→群里一句「暂无新报销」（`--no-new`），不发负责人长文。~~旧规则：无论有无都发两层、无变化也发私聊状态行、有重复也发详细通报——已作废。~~ 未报销/未结只认「已登记·待打款」，其余状态金额不进合计。**不发司机私聊**（配置禁用 + 发送端硬拦截）。
- **司机版只讲金额、日期**（2026-11-16 20:08 起不再 @报销人、不贴任务链接）：只列本轮有凭证的司机；异常一行小提示、结尾必带一句安全驾驶调侃；四态/未结/环比/笔数/订单号/文件名/台账路径/未写报表原因绝不进司机版。~~（任务链接是 2026-11-14 23:53 用户明确要求贴出的例外，已作废。）~~
- **任务权限隔离（仅任务内部，不进通知）**：负责人（assignee）可编辑；报销人仅以 follower 查看/评论，不能改金额或点完成。需要其 open_id；缺失时**静默跳过并仅记清单**，不作待办或催办，不影响入账与负责人编辑。~~真实报销后点完成任务 → 群内 @报销人发极简确认~~ **已作废**（`group_task.notify_on_complete=false`：完成后只台账标记已报销，不再群内 @）。
- **只认付款凭证截图**：手写票一律不入账、不登记台账（但要发补录提醒）；纯文本报销消息一律忽略；两者都不得因「金额可辨」而写入。**规则本身不变**；用户在某轮对个别问题图作「特批通过」时，须在清单与专业版标注「按用户指示本轮特批、规则不变、后续由用户提醒司机」，绝不把例外写进规则。
- **无报表文件的司机绝不新建报表**：不新建 xlsx 文件；找不到文件就 `record_without_write`（台账 `no_report=1` + 确认任务 + 专业版注明待指定报表）。陈华胜目前仍无 2026 报表文件。
- **唯一建 sheet 例外（用户 2026-11-14 23:53 授权）**：允许在**已存在**的年份报表内新建唯一一个「报销明细」sheet，且只允许 `scripts/reimb_detail.py` 用 zip 层精确插入（备份 + 回读校验 + 失败回滚）。除此之外不新建 sheet、不插入行到原有 sheet、不删行列、不覆盖公式、不改其他列。
- 只写入 `报表根/{YYYY}年/司机工资/` 下与司机同名年份文件的**「报销明细」sheet**；原有报销汇总单元格一律不写，避免双记。**明细 sheet 可见列固定为日期 / 订单号 / 类型 / 金额(元) 4 列**（第 5 列隐藏存幂等键），按凭证月份分节；绝不把商户、文件名、消息时间、任务链接、备注等技术字段再写回报表。
- 每笔写入必须先备份；台账登记必须在回读校验成功之后；清单累计追加，不覆盖。
- 定时运行无人值守：不做逐条事前确认，采用「先备份 + 幂等台账 + 写入后清单 + 通报」。用户明确要求「只出清单不写入」时，跳过第 7 步写入与台账登记。
- 云端 WPS 同名目录（`我的云文档/WPS/冷链物流/2026年/司机工资`）**默认不写**；如需云端同步，须用户显式把 `cloud_sync.enabled` 设为 true 并按 `references/report-layout.md` 的映射执行，避免本地与云端各自累加造成双记。

# 通讯、确认闸门与防发错人

## 一、通道选型

需求里「怎么通讯你想办法」的结论：**默认走飞书逐人私聊（`--user-id` 直发）**，理由是：

- 现成的一对一通道，无需先建会话，也不需要把司机拉进同一个群；
- 有 `open_id` 精确标识，可做白名单硬校验，避免按姓名模糊匹配发错人；
- 支持幂等键，重复运行不会刷屏；
- 与既有报销系统使用同一套发送约定，运维成本最低。

适配器是可替换的（`scripts/notify.py`）：

| channel | 行为 |
|---|---|
| `dry-run` | 只生成 `dispatch.json` 预览，绝不外发（样例 profile 默认） |
| `stdout` | 打印到本地，用于自测 |
| `feishu` | **生产通道（2026-11-14 定案）**。逐人私聊；群内通知仅用于「发起人待确认」，绝不用于工资条 |
| `email` / 企业微信 | 预留：在 `notify.py` 增加一个发送函数即可，闸门与幂等逻辑完全复用 |

**调用层仍然默认 dry-run**：`dispatch` 不带 `--no-dry-run` 时，即便 `channel=feishu` 也绝不外发。

**工资是敏感数据**：一人一条、只含本人，绝不群发，绝不把个人工资条降级发到群里。这与"报销金额可公开"是两套口径，不要混用。

## 二、三段式外部动作（严格区分）

| 阶段 | 收件人 | 内容 | 是否需确认 |
|---|---|---|---|
| `preview` 的通知 | **发起人本人** | 核对结论、合计、报告路径、工资表路径、确认口令、阻断/复核项 | 不需要，但**不是工资条** |
| `confirm` | 无外发 | 记录确认人、时间、token、结果指纹 | — |
| `dispatch` | **每位司机本人** | 本月工资条（应发/报销/扣款/实发/趟数）+ 本人明细附件 | **必须在确认之后** |

定时任务只做第一段，绝不执行第三段。

## 三、确认闸门（硬）

`scripts/gate.py` 在 `dispatch` 前逐条校验，任一不满足即抛错，不降级、不代确认：

1. 结果文件内容重算指纹与 `result_hash` 一致（防篡改）；
2. 核对结论不是 `BLOCK`；
3. `confirmation.json` 存在且确认人 == `gate.owner`；
4. 确认记录的 `result_hash` / `input_hash` 与当前结果一致（确认后改动即失效）；
5. 核对报告与计算结果指纹一致、结论未变；
6. 确认未过 `confirm_ttl_hours`（默认 72h）；
7. 若结论为 `REVIEW`，确认记录须带 `accept_review=true`。

token 由 HMAC-SHA256 生成，绑定 `月份 | 结果指纹 | 核对结论`，密钥取自环境变量
`PAYROLL_GATE_SECRET`，否则用 `state/gate_secret`（权限 600）。**Agent 不得自行编造 token 或代替发起人确认**。

## 四、逐司机私发的硬校验

- 司机必须在 `roster.drivers` 内，且 `notify=true`；
- **启用飞书主源时，还须 `feishu=true`**（由 `sync-roster` 标记）。仅在本地名册的司机只作信息记录，不私发、不进 `missing_open_id`、不当异常或催办；
- `open_id` 必须存在且以 `ou_` 开头；缺失或格式不对（例如误把 `chat_id` 填进来）一律**跳过并列出名单**，绝不猜；
- 每条消息只含该司机本人的数据，绝不出现其他司机姓名或金额；
- 幂等键 `payroll-dm:<月>:<司机>:<结果指纹前8位>`；`state/<月>/sent.json` 记录已成功发送者，同月同司机不重发（`--force` 才覆盖）；
- 单人失败不影响其他人；失败原因写进 `dispatch.json` 与 `audit.jsonl`；
- 私聊发送失败**只允许记为失败**，绝不降级发到群里（否则会把别人的工资公开）；
- 群 chat_id 若用于发起人通知，必须精确匹配配置，禁止按群名搜索或模糊匹配。

## 五、名册以飞书为主源、人数弹性（2026-11-14 定案）

司机名册常来自报表文件名（本地 Excel），而飞书里真实可联系到的司机可能少得多。
用户定案：**以飞书司机数为主，有几个司机计算几个**。

| 维度 | 口径 |
|---|---|
| 名册主源 | `sync-roster` 从飞书通讯录部门 + 群成员拉取真实成员，排除群主/机器人/外部成员 |
| 本地名册 | 只作补充，用于运输单归属与报表定位，不决定计算人数 |
| 计算范围 | 当月实际有运输单/报销的司机，**有几个算几个**，不铺零值行、不凑人数 |
| 私发范围 | **只发飞书在册**且 `open_id` 有效者；其余进 `dispatch.json.skipped` 仅作信息记录 |
| 不做什么 | 不催 open_id、不催进群、不把「谁没到齐」列成异常/待办、不按姓名猜归属 |

当前真实环境：飞书在册 1 位司机，名册 9 人，当月有单 7 人 → 计算 7 人工资、只向 1 人私发。
这正是预期口径，不是故障。`preview.roster` 会同时打印这三个数字供发起人核对。

飞书不可用或缓存为空时：保留旧缓存、标记 `stale`、可私发对象为 0，
**绝不伪造名册**；`sync-roster` 失败不会覆盖已有缓存。

## 六、审计

`state/<月>/audit.jsonl` 逐条记录：`compute` / `verify` / `preview` / `notify_owner` /
`confirm` / `dispatch_dry` / `dispatch_driver` / `dispatch_done`，含时间、结论、指纹、司机、幂等键、成败原因。
`dispatch.json` 含确认人与确认时间，可完整复盘"谁在什么时候批准了哪一份结果、发给了谁"。

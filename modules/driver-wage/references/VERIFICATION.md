# 核对工资：判定口径

核对的目标不是"把结果再打印一遍"，而是**从原始输入走另一条实现路径，证伪计算结果**。
结论只有三种：`BLOCK`（硬错误）/ `REVIEW`（需人工复核）/ `PASS`。

**范围口径（2026-11-14 定案）**：名册以飞书司机数为主、飞书优先＋本地补充；
计算只覆盖当月**实际有运输单/报销**的司机，有几个算几个。核对报告头部会打印
「计薪范围：N 位司机（名册 M 人，其中飞书在册 K 人）」。名册里有人当月没单
不构成异常、不构成待办、不催办；名册人数与计算人数不同也不触发核对失败。

## 八类检查

### 1. integrity · 结果完整性（硬）
- 重算 `result_hash` 并与文件内字段比对（不信任写着的 hash）。
- 校验月份、schema、`input_hash` 存在。
- `gate` 在 dispatch 前**再做一次内容级重算**，防止有人改了 totals 却没改 hash。

### 2. recompute · 独立路径重算（硬）
- 重新从原始文件读运输单（不看 `payslips.json`）。
- 用另一套聚合实现逐行算工资、逐司机累加，与结果的 `gross` 比。
- `tier` 用线性扫描、`lookup` 直接查表、`const` 直接取、`sum` 递归；只有 `formula` 复用安全求值器（见 `RULE_DSL.md` 的诚实边界）。
- 容差 `checks.amount_tolerance`（默认 0.01）。

### 3. completeness · 数据完整性（硬 / 复核）
| 项 | 判定 |
|---|---|
| 司机未映射名册或别名 | **硬阻断**（绝不猜归属） |
| 疑似重复运输单（默认键 `driver+date+route+km+trip_no`） | **硬阻断**（重复直接多算钱） |
| 公里数 ≤0 或 > `max_km` | **硬阻断** |
| 日期不属于目标月份 | **硬阻断** |
| 输入适配阶段产生警告 | 复核 |
| 名册人数 ≠ 计算人数 | 仅记录，不算异常（弹性名册，不铺零值行、不凑人数） |
| 按名册筛除的外部司机行数 | 记录，透明可见，不算异常 |

### 4. balance · 三层勾稽（硬）
- 逐行工资和 + 固定加项 = 每人应发；
- 应发 + 报销 − 扣款 = 实发；
- 各司机之和 = 全员合计（gross / reimbursement / deduction_total / net 四个字段都查）。

### 5. rule_compliance · 规则合规（硬）
- 每位有单司机必须有规则；
- **规则必须 `confirmed=true`**（未确认禁止据此发薪）；
- 规则可求值、计算阶段无错误。

### 6. reimbursement · 报销口径（硬 / 复核）
- 报销数据源合计 vs 计入工资合计，不一致硬阻断；
- 未映射司机的报销记录不计入并提示人工确认；
- 可选：与历史工资表底部「报销 / 报销支出」汇总块做**三方比对**。真实环境两个系统口径常不同（台账按凭证逐笔、工资表是手工汇总数），差异必须人工裁决以哪份为准，绝不自动取其一。

### 7. variance · 环比与异常金额（阈值可配）
- 实发为负 → 硬阻断；
- 与上月实发波动 > `variance_block_pct`（默认 90%）→ 硬阻断；
- > `variance_warn_pct`（默认 30%）→ `REVIEW`，需发起人显式接受；
- 无历史基线时跳过该项并降级说明，不假装通过。

### 8. external_bill · 外部账单交叉验证（可选 / 复核）
- 账单常自带「核对费用 / 核对差异」列；差异不为 0 说明**运输单本身**可能有问题，工资算得再准也白搭；
- 启用后列出差异行；未配置则标 `SKIP`，不伪装成通过。

## 判定与后果

| 结论 | 条件 | 允许 |
|---|---|---|
| `BLOCK` | 任一检查 `FAIL` | 修正输入 → 重新 compute + verify。**禁止 confirm / dispatch** |
| `REVIEW` | 无 `FAIL`，有 `WARN` | confirm 必须带 `--accept-review` |
| `PASS` | 全通过 | confirm → dispatch |

`verification.json` 供程序读取，`verification.md` 供发起人阅读（表格 + 每项明细 + 后续动作说明）。
发起人在 `confirm` 前应当实际打开 `verification.md` 与统一工资表核对，token 只是技术闸门，不替代人工判断。

## 处理阻断的推荐顺序

1. 看 `verification.md` 的「不通过」段落，定位到具体检查项。
2. 规则未确认 → 走 `RULE_DSL.md` 的确认流程；`needs_manual` 的司机手工补录。
3. 无规则 / 未映射司机 → 补 `rules.drivers` 或 `driver_aliases`（别名不一致是真实报表高频问题）。
4. 重复单 → 检查是否同一趟被多个 `trips_sources` 读了两遍；**同一趟只能进一个来源**。
5. 报销口径差异 → 人工裁决唯一口径，关闭另一来源，不要两边都加。
6. 环比异常 → 先确认不是规则改错或数据漏单，再考虑显式接受。
7. 修完重新 `compute` + `verify`；**不要直接改 `payslips.json`**（会触发内容级防篡改）。

## 绝不发生的情形

- BLOCK 仍生成可确认的 token 并被放行；
- 靠"把 FAIL 改成 PASS"消除阻断；
- 核对跳过任何一类检查且不标注 `SKIP`；
- 用计算阶段的结果对象当作核对的证据（自证）；
- 因核对失败而删除/覆盖历史工资表。

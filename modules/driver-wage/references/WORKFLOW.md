# 工作流与状态机

## 一、两件事，一条链

```
[输入准备]                    [① 计算工资]        [② 核对工资]          [交付编排]
运输单(图片/报表) → 筛选/映射 ┐
报销数据 → 只读汇总           ├→ compute ────→ verify ────→ preview ─→ 发起人确认 ─→ dispatch
历史工资表 → 反推规则(需确认)┘      │               │              │            │            │
统一模板 → 抽取样式 ────────────────┘               │              │            │            │
                                          payslips.json  verification.*  workbook    confirmation
                                                                      预览+token    逐人私发
```

`compute` 与 `verify` 是仅有的两个业务能力。其余环节只是让这两件事有输入、有输出，**不得扩张成第三个业务功能**。明确排除：报销归集、运费结算、车贷/油耗/管理费/净利润、考勤、社保、个税、报表写回、绩效分析。

## 二、状态机

| 状态 | 进入条件 | 允许的动作 | 禁止的动作 |
|---|---|---|---|
| `EMPTY` | 无结果 | compute | verify / confirm / dispatch |
| `COMPUTED` | compute 成功 | verify | confirm / dispatch |
| `BLOCK` | verify 有硬错误 | 修正输入后重新 compute | **confirm / dispatch / 任何私发** |
| `REVIEW` | verify 仅有复核项 | confirm（须 `--accept-review`） | 无显式接受时 dispatch |
| `PASS` | verify 全通过 | confirm | 未确认时 dispatch |
| `CONFIRMED` | 发起人确认且指纹未变 | dispatch | 修改输入/规则/结果（会使确认失效） |
| `DISPATCHED` | 已投递 | status 查询 | 同月同司机重复投递（幂等） |

任何输入、规则或结果变化都会改变 `input_hash` / `result_hash`，使 `CONFIRMED` 回退到 `COMPUTED`，必须重新核对与确认。这是防止"确认后被改动"的核心机制。

## 三、每月 10 号自动化的边界

- RRULE：`FREQ=MONTHLY;BYMONTHDAY=10;BYHOUR=9;BYMINUTE=0`（Asia/Shanghai）。
- 自动化**只发起计算与核对**，运行到 `preview` 为止：产出统一工资表、逐司机工资条、核对报告、待确认 token，并通知发起人。
- **自动化绝不代替发起人确认，绝不自动 dispatch**。发薪是有外部后果的动作，人工闸门不可省。
- 统计月份默认「上个月」；先执行 `sync-roster` 同步飞书名册，再 `preview`。若物料不齐（缺运输单 / 规则未确认），自动化仍产出核对报告并说明阻断项，不静默跳过、不以空数据当成功。
- 「名册缺 open_id / 司机没到齐」**不再是异常、待办或催办理由**：按弹性口径只作信息记录，不影响计算与核对。
- 发起人确认后，由一次独立会话执行 dispatch。

## 四、需求补全清单（原需求未覆盖、但发薪必须有）

| # | 补全点 | 不补会怎样 |
|---|---|---|
| 1 | 从历史工资表反推的规则**必须逐条人工确认**，`confirmed=false` 一律阻断 | 反推错算法会直接算错全月工资 |
| 2 | 核对前先做数据质量门禁：重复单、未映射司机、日期/公里数越界 | 一趟重复计薪、外部司机混入 |
| 3 | "筛选数据"的结果要**透明记录筛除行数**，并在报告中可见 | 悄悄丢单无法追责 |
| 4 | 结果指纹 + 输入指纹 + 确认绑定；确认后改动即失效 | 确认后被改数，等于没确认 |
| 5 | 确认人身份校验 + 确认有效期 | 任何人/任何时间都能拿旧口令放行 |
| 6 | 所有外发默认 dry-run，需显式关闭 | 调试时误发真实工资 |
| 7 | 一人一条、只含本人；绝不群发、绝不降级到群 | 工资隐私事故 |
| 8 | 只私发飞书在册且 open_id 有效的司机；本地名册司机仅信息记录，绝不猜、绝不按姓名模糊匹配 | 发错人、把不在飞书的人催成待办 |
| 9 | 幂等：同月同司机只发一次，键含结果指纹 | 重复打扰、重复打款暗示 |
| 10 | 全程只读原始文件，产物只进 `out_dir` | 破坏历史工资表/报销台账 |
| 11 | 图片运输单的转录契约（视觉转录 → 结构化文件，低置信度不猜） | OCR 幻觉直接进工资 |
| 12 | 金额全链路 Decimal + 明确取整口径 | 0.01 误差引发无谓争议 |
| 13 | 核对报告要有人类可读版（`verification.md`）供发起人签字前看 | 只有 JSON 没法人工确认 |
| 14 | 弹性人数：只算当月实际有单/报销的司机，不铺零值行、不凑人数 | 名册凑数掩盖漏单、把未实际出车的人算进工资表 |
| 15 | 报销口径三方勾稽（台账 / 历史工资表汇总块 / 本次计入） | 两个系统口径不同，重复或漏加 |
| 16 | 外部账单「核对差异」列交叉验证运输单可信度 | 输入本身错了，工资算得再准也错 |
| 17 | 环比历史工资异常阈值（复核线 / 阻断线） | 规则改错导致全员工资翻倍无人察觉 |
| 18 | 逐行明细可回溯到来源文件与行号 | 争议时无法定位 |
| 19 | 审计日志（计算/核对/确认/投递全留痕） | 事后无法复盘 |
| 20 | 开源隔离：真实姓名/金额/路径/open_id 只在 gitignore 的 `config/local/` | 一开源就泄露员工薪资 |
| 21 | 名册主源是飞书真实成员（`sync-roster`），本地名册只作补充；飞书不可用时降级但不伪造 | 拿过期名册发薪、凭姓名猜 open_id |
| 22 | 通道 `feishu` 仍默认 dry-run；私发名单收敛到飞书在册 | 一次点击把工资条发给不在册的人 |

## 五、异常处理原则

- 异常**不得静默**：全部进 `payslips.warnings` / `errors` 与 `verification.md`。
- 同类逐行错误在报告里聚合计数，逐行坐标仍保留在 `lines`，既不刷屏也不丢信息。
- 单个司机投递失败不影响其他司机；失败原因写进 `dispatch.json` 与审计日志。
- 任何失败都不回滚已生成的计算产物（可追溯），但会阻止后续确认与发送。
- 规则求值失败绝不填 0、绝不"按平均估一个"，该行工资留空并阻断。

## 六、文件产物

```
out/<YYYY-MM>/
├── payslips.json          逐行明细 + 每人汇总 + 全员合计 + 输入指纹
├── verification.json      8 类核对结论（机器可读）
├── verification.md        核对报告（发起人阅读）
├── 工资表_<YYYY-MM>.xlsx  统一格式：汇总 sheet + 明细 sheet
├── payslips/              每位司机一份 xlsx + 一条纯文本工资条
└── dispatch.json          逐人投递结果、缺失 open_id 名单
state/feishu_roster.json   飞书名册缓存（只读、gitignore）
state/<YYYY-MM>/
├── preview.json           待确认预览 + token
├── confirmation.json      发起人确认记录
├── sent.json              幂等状态
└── audit.jsonl            全链路审计日志
```

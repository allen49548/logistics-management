# 分层架构设计方案（可复用）

> 目标：把「具体业务规则」从通用引擎和外部交互中彻底抽离，形成 **Core / Business / Operations** 三层单向依赖结构。  
> 本文既是设计规范，也是 `blueprint/` 参考实现的设计依据。参考实现可整体复制到其他项目使用。

---

## 0. 设计原则

| 原则 | 含义 |
|---|---|
| 高内聚 | 同一层内只放同类关注点：核心层只放通用机制，业务层只放规则与流程，操作层只放 I/O 与适配 |
| 低耦合 | 层与层之间只通过 Core 定义的 Port / DTO / Result 交互 |
| 单向依赖 | 源码依赖只允许 `Business → Core`、`Operations → Core`、`Composition → 三层` |
| 依赖倒置 | 业务层依赖抽象 Port，不依赖具体适配器；适配器实现 Port 后由组装根注入 |
| 稳定核心 | Core 不含任何业务词汇，接口只增不减，变更走版本化契约 |
| 业务可插拔 | 新增场景只新增 Business 包并注册；不改 Core / Operations |
| 渠道可替换 | 新增外部系统只新增 Operations 适配器；不改 Business / Core |

三条硬约束：

1. **核心层不感知业务**：源码中不出现司机、报销、工资、车贷、凭证、月份等业务名词。
2. **业务层不碰外部 I/O**：不出现文件路径、网络客户端、表格库、CLI 参数、数据库驱动。
3. **操作层不做业务判断**：不判断「是否允许」「金额多少」「是否重复」「通知谁」，只执行已生成的 Decision / Result。

## 1. 各层职责与不负责内容

### 1.1 Core 核心层

**目录**：`blueprint/core/`

**负责**

- 通用数据模型：`Result[T]`、`Error`、`Context`、`Envelope`。
- 抽象端口：`Handler`、`Reader`、`Writer`、`Notifier`、`Clock`、`UnitOfWork`、`Interceptor`。
- 通用执行引擎：`Runner`：拦截器、异常兜底、结果封装，不含场景逻辑。
- 策略抽象：`Policy`、`Decision`，只定义「输入 → 判定」的形状。
- 扩展注册：`Registry[T]`，按名称注册用例/插件。
- 通用校验原语：非空、类型、范围等无业务语义的校验。

**不负责**

- 任何业务名词、业务规则、业务流程、业务状态机。
- 读配置文件、读环境变量、读数据库、发消息、写表格。
- 具体协议：HTTP / MCP / CLI / Feishu / xlsx / sqlite。
- 具体时间格式、金额口径、去重口径、权限口径。

**稳定性要求**：Core 是最稳定的包；新增能力优先加新 Port 或新版本契约，不修改既有签名。

---

### 1.2 Business 业务层

**目录**：`blueprint/business/`

**负责**

- 场景 DTO：`contracts.py` 中定义请求/响应对象，是业务词汇唯一允许出现的位置之一。
- 纯业务规则：`policies/` 或 `rules.py`，例如「必须凭证」「同键去重」「周期归属」「通知门控」。
- 流程编排：`workflows.py` / `UseCase` 实现，按序调用 Policy、通过 Core Port 触发副作用、返回 `Result`。
- 业务决策：`Decision` 表达「通过 / 拒绝 + 原因」，由业务层产生。
- 业务错误：如 `REJECTED_NO_PROOF`、`DUPLICATE_REFERENCE`。

**不负责**

- 不 import `operations`、`composition`。
- 不实例化具体适配器；所有外部能力由构造函数注入的 Core Port 提供。
- 不做序列化、重试、超时、限流、日志落地、命令行解析。
- 不读取本地路径、环境变量、密钥；只使用已注入的配置参数。

**可测试性**：用内存 Fake Port 即可完成全部业务单测，无需飞书、Excel 或数据库。

---

### 1.3 Operations 操作层

**目录**：`blueprint/operations/`

**负责**

- 适配器：实现 Core Port，如 `InMemoryReader`、`RecordingNotifier`、`SystemClock`；真实项目中对应 Feishu / xlsx / sqlite / lark-cli。
- 驱动：`CliDriver`、`McpDriver` 等，把外部输入封装为通用 `Envelope`，调用注入的 `Handler`。
- 映射：外部 JSON / 表格行 ↔ 通用 dict；业务 DTO 的构造交给 Composition。
- 技术韧性：超时、重试、限流、连接池、错误码映射为 Core `Error(kind="external")`。
- 输出：把 `Result` 序列化为 stdout / HTTP / MCP 响应。

**不负责**

- 不解释业务语义：不判断金额是否合法、不决定是否通知、不实现去重规则。
- 不 import `business`；不构造业务 DTO。
- 不保存业务状态、不维护流程进度。
- 不反向调用用例：驱动只调用注入的 `Handler`。

---

### 1.4 Composition 组装根

**目录**：`blueprint/composition/`

它不是「第四业务层」，而是唯一允许同时看见三层的装配点。

**负责**

- 创建 Operations 适配器。
- 把适配器注入 Business UseCase。
- 把 UseCase 注册到 Core `Registry`。
- 实现 `Handler`：把通用 `payload` 映射为业务 DTO，再交给 `Runner`。
- 按 profile 切换 `memory` / `production` 绑定。

**不负责**

- 不写业务规则、不写外部 I/O 实现、不写通用引擎。

## 2. 依赖方向与调用链路

### 2.1 源码依赖（编译期，单向）

```text
          ┌──────────────┐
          │     Core     │  ← 被依赖，不依赖任何上层
          └──────▲───────┘
                 │
      ┌──────────┴──────────┐
      │                     │
┌─────┴─────┐         ┌─────┴─────┐
│  Business │         │ Operations│
└─────▲─────┘         └─────▲─────┘
      │                     │
      └──────────┬──────────┘
                 │
          ┌──────┴──────┐
          │ Composition │  ← 唯一可 import 三层
          └──────▲──────┘
                 │
          ┌──────┴──────┐
          │  Entrypoint │  CLI / MCP / 定时任务
          └─────────────┘
```

允许：`Business → Core`、`Operations → Core`、`Composition → Core/Business/Operations`、`Entrypoint → Composition + Operations`。  
禁止：`Core → 任何上层`、`Business → Operations`、`Operations → Business`、`Business/Operations → Composition`。

### 2.2 运行时调用链

```text
Entrypoint / Driver
   │ 构造 Envelope(command, payload, ctx)
   ▼
Composition.Container.handle()
   │ 1. payload → 业务 Request（唯一映射点）
   │ 2. Registry 取 UseCase
   ▼
Core.Runner.run()
   │ 拦截器 / 异常兜底（通用）
   ▼
Business.UseCase.execute()
   │ 调用 Policy → 得到 Decision
   │ 通过 Core Port 发起副作用
   ▼
Core Port（接口）
   │ 依赖倒置
   ▼
Operations.Adapter（实现）
   │ 真正读写外部系统
   ▼
External System → 返回值逐层以 Result / DTO 回传
```

关键：**业务层调用的是接口，操作层实现的是接口；二者在源码上互不认识，只在运行时由 Composition 绑定。**

## 3. 模块边界与接口契约

### 3.1 Core 对外契约

| 契约 | 形状 | 说明 |
|---|---|---|
| `Result[T]` | `ok / value / error` | 所有跨层返回统一封装 |
| `Error` | `code / message / kind / details` | `kind` 仅 `technical / business / external` |
| `Context` | `request_id / actor / occurred_at / metadata` | 通用执行上下文，不含业务字段 |
| `Handler` | `handle(command, payload, ctx) -> Result` | 驱动唯一可调用的入口 |
| `Reader` / `Writer` | `read(key, ctx)` / `write(key, records, ctx)` | 通用存取端口 |
| `Notifier` | `notify(channel, payload, ctx)` | 通用通知端口 |
| `Clock` / `UnitOfWork` | `now()` / 上下文管理 | 时间与事务抽象 |
| `Policy[I,O]` | `evaluate(candidate, ctx) -> Decision[O]` | 规则形状，不含规则内容 |
| `UseCase[Req,Res]` | `execute(request, ctx) -> Result[Res]` | 用例形状 |
| `Interceptor` | `before / after` | 横切扩展点 |
| `Registry[T]` | `register / get / names` | 命名扩展点 |

### 3.2 契约规则

1. **Port 定义在 Core，实现在 Operations**，业务层只持有 Port 引用。
2. **跨层只传 DTO / 基本类型 / `Result`**，禁止传 ORM 模型、SDK 对象、文件句柄。
3. **业务 DTO 由 Business 定义，由 Composition 构造**；Operations 只传 dict。
4. **Decision 由 Business 产生，由 Business 消费**；Operations 不解析 `reason` 做分支。
5. 契约版本化：破坏性变更新增 `core/contracts/v2/`，旧版本保留适配期。
6. 命名约定：
   - `core/`：机制名，`runner / ports / policy / registry / model`。
   - `business/`：场景名 + 角色名，`contracts / rules / workflows`。
   - `operations/`：渠道名 + 角色名，`adapters / drivers / mappers`。
   - `composition/`：装配名，`container / bootstrap / profiles`。

## 4. 层间交互约束（可机器检查）

| # | 约束 | 检查方式 |
|---|---|---|
| C1 | `core/` 不得 import `business / operations / composition` | AST 扫描 import |
| C2 | `core/` 源码不得出现业务词汇 | 关键字扫描 |
| C3 | `business/` 不得 import `operations / composition` | AST 扫描 import |
| C4 | `operations/` 不得 import `business / composition` | AST 扫描 import |
| C5 | 仅 `composition/` 可同时 import 三层 | AST 白名单 |
| C6 | 业务层副作用必须经 Core Port | 代码评审 + 禁止 SDK import |
| C7 | 操作层不得根据业务字段做分支 | 代码评审 + 规则函数命名检查 |
| C8 | 配置/密钥只在 Operations 读取，经 Composition 注入 | 静态扫描 `open / os.environ` |
| C9 | 错误映射：Business 产业务错误，Operations 产外部错误，Core 只兜底技术错误 | `Error.kind` 约束 |
| C10 | 禁止跨层全局单例 | 只允许 Composition 持实例 |

`blueprint/tests/test_layers.py` 落实 C1–C5；其余作为评审规则写入本文档。

## 5. 扩展点与复用方式

### 5.1 扩展点

| 想扩展什么 | 改哪里 | 不改哪里 |
|---|---|---|
| 新增业务场景 | `business/` 新增 rules + workflow，Composition 注册 | Core、Operations |
| 修改业务口径 | 只改 `business/rules.py` / `policies/` | Core、Operations、驱动 |
| 新增外部渠道 | `operations/adapters/<channel>.py` 实现已有 Port | Business、Core |
| 新增入口 | `operations/drivers/<driver>.py` 调用注入的 Handler | Business、Core |
| 新增横切能力 | Core `Interceptor` 实现并在 Composition 注册 | 各层业务代码 |
| 新增执行环境 | `composition/profiles.py` 增加 profile 绑定 | 业务代码 |

### 5.2 复用方式

- **整包复用**：复制 `blueprint/` 到新项目，替换 `business/` 与 `operations/adapters/` 即可。
- **按层复用**：`core/` 可独立作为通用引擎；`operations/adapters/memory.py` 可直接作为测试替身库。
- **按场景复用**：多个 `UseCase` 共享同一组 Port 与 Runner，避免重复造轮子。
- **按环境复用**：`memory` profile 用于单测，`production` profile 绑定真实适配器，业务代码零改动。

### 5.3 测试策略

- Core：纯单测，验证 Runner、Registry、Result。
- Business：用 `InMemoryReader/Writer/RecordingNotifier` 做 Fake，覆盖全部规则分支。
- Operations：契约测试，验证每个 Adapter 满足 Core Port。
- Composition：集成测试，验证绑定与端到端链路。

## 6. 文件目录结构

```text
logistics-management/
├── docs/
│   └── 分层架构设计.md              # 本方案
├── blueprint/                       # 可复制的参考实现，不依赖现有业务模块
│   ├── __init__.py
│   ├── core/                        # 通用稳定层：零业务语义
│   │   ├── __init__.py
│   │   ├── model.py                 # Result / Error / Context / Envelope
│   │   ├── ports.py                 # Handler / Reader / Writer / Notifier / Clock / UoW
│   │   ├── policy.py                # Policy / Decision
│   │   ├── usecase.py               # UseCase / Interceptor / Runner
│   │   └── registry.py              # Registry[T]
│   ├── business/                    # 业务层：场景规则与流程
│   │   ├── __init__.py
│   │   ├── contracts.py             # 业务 DTO
│   │   ├── rules.py                 # 纯业务规则
│   │   └── workflows.py             # UseCase 编排
│   ├── operations/                  # 操作层：执行、适配、外部交互
│   │   ├── __init__.py
│   │   ├── adapters.py              # Port 实现（示例为内存版）
│   │   └── drivers.py               # CLI 驱动
│   ├── composition/                 # 唯一组装根
│   │   ├── __init__.py
│   │   ├── container.py             # 绑定 + 注册 + Handler
│   │   └── bootstrap.py             # build() / main()
│   └── tests/
│       ├── test_layers.py           # 依赖方向守卫
│       └── test_flow.py             # 端到端脱敏流程自测
├── scripts/                         # 现有统一入口（保持不动）
├── modules/                         # 现有内置业务模块（保持不动）
└── README.md                        # 增加架构与 blueprint 导航
```

结构特点：每层目录浅、文件名即职责、无 `utils / common / misc` 兜底包；新增能力优先加文件而不是加层级。

## 7. 与现有系统的迁移映射（建议，不在本轮改动）

| 现有位置 | 目标层 | 迁移动作 |
|---|---|---|
| `scripts/logistics.py` 路由 | Operations.Driver / Composition | 收敛为 Handler 调用 |
| `scripts/agent_runtime.py` 安全门 | Core.Interceptor + Business.Policy | 通用拦截与业务判定拆开 |
| `modules/reimbursement/scripts/*` 去重与口径 | Business.Rules | 抽成纯函数 |
| `modules/reimbursement/scripts/*` 飞书调用 | Operations.Adapter | 实现 Notifier / Reader Port |
| `modules/driver-monthly-sheet/scripts/*` xlsx 写入 | Operations.Adapter | 实现 Writer Port |
| `config/modules.json` | Composition.Profiles | 从「脚本路径表」升级为「绑定表」 |
| `tests/test_skill.py` | Blueprint.Tests | 增加依赖守卫 |

迁移分三步，旧入口全程保留为兼容驱动：

1. 抽 Port 与 DTO，现有脚本先实现 Port。
2. 把规则函数搬入 Business，用 Fake Port 补齐单测。
3. Composition 切换绑定，逐步下线脚本内直接 I/O。

## 9. 一句话总结

**Core 提供「怎么跑」，Business 决定「做什么、按什么规则」，Operations 负责「跟外面怎么打交道」；三者只在 Composition 相遇，从此改规则不动引擎，换渠道不动业务。**
